# RV32 machine: contract and first firmware

This document fixes the machine contract for our RISC-V computer and describes the first firmware image built against it. It is our own small machine, not a Linux-capable platform and not a copy of QEMU's `virt` board: three addresses were chosen to coincide with `virt` so QEMU can serve as an independent reference runner, nothing else is borrowed. SAP8 remains the separate teaching CPU.

Primary sources: the [RV32I chapter](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html) of the RISC-V unprivileged specification (RV32I version 2.1) and the [RISC-V ELF psABI](https://github.com/riscv-non-isa/riscv-elf-psabi-doc) (integer calling convention, `e_flags`).

## Implementation plan (M1)

1. Record actual tool paths and versions; read the ISA chapter and psABI before fixing the contract.
2. Write the contract below: reset, byte order, address map, memory transactions, alignment and faults, supported ISA, and the console/done protocol.
3. Complete the cross toolchain: Homebrew Clang 22 compiles RV32I, Homebrew lld links it, QEMU runs it.
4. Add startup assembly, a linker script, the multiply/divide runtime, and a C self-check with hand-computed expected values.
5. Execute the image on QEMU and require the console line and exit status to agree.
6. Add build/validation commands without touching the default counter target; write the [C-to-instructions walkthrough](c-to-instructions.md).

All six steps are complete; see [Milestone result](#milestone-result).

## Supported ISA and privilege

- RV32I version 2.1: 32 registers with `x0` hardwired to zero, 32-bit instructions only. No M, A, F, D, or C extensions. Multiplication and division are runtime routines.
- ILP32 soft-float C ABI: `int`, `long`, and pointers are 4 bytes; arguments in `a0`–`a7`, results in `a0`/`a1`; `s0`–`s11` callee-saved; `sp` 16-byte aligned at every call; integers narrower than 32 bits are widened according to their own signedness.
- Little-endian memory. `FENCE` completes with no effect: one hart, no caches.
- Planned machine: machine mode only. `ECALL`, `EBREAK`, illegal instructions, misaligned accesses, and accesses outside the map trap through `mtvec` with `mcause`/`mepc`/`mtval`; interrupts are later work. The emulator (M2) implements this trap contract; see [Behavior fixed in M2](#behavior-fixed-in-m2).
- M1 slice: no CSR instructions are used or required. There is no trap handler; a trap on the reference runner vectors to the reset value of `mtvec`, address 0, which has no memory, so the run hangs and the driver reports a timeout. This is a recorded limitation, not an accepted behavior.

## Reset

At reset the PC is `0x8000_0000`. Every other register is unspecified, so firmware must not read one before writing it. Memory holds the firmware image at its link addresses; other RAM contents are unspecified and `.bss` is zeroed by startup code.

QEMU reconciliation: `qemu-system-riscv32 -M virt -cpu rv32i -bios none -kernel image.elf` runs a mask ROM at `0x1000` that loads `a1` with a device-tree pointer, would load `a0` with the hart id (a `csrr`, executed as `nop` on the CSR-less `rv32i` model), and jumps to the DRAM base `0x8000_0000`. This was verified with `-d in_asm`. Our image therefore does not rely on the ELF loader honoring `e_entry`: the build asserts `e_entry == _start == lowest load address == 0x8000_0000`, and `_start` is the first instruction of the image.

## Memory map

| Region | Base | Size | Planned machine | M1 slice |
| --- | --- | --- | --- | --- |
| Done register | `0x0010_0000` | 4 bytes | A word write ends the run | Same |
| Console | `0x1000_0000` | 8 bytes | TX byte at +0, status at +5; this is the debug output | Same |
| Timer | `0x2000_0000` | 16 bytes | Free-running tick counter (M5) | Absent |
| Input | `0x2000_1000` | 16 bytes | Key event queue and held-key mask (M5) | Absent |
| Display | `0x2000_2000` | 16 bytes | Present, frame count, resolution (M5); a palette window at `0x2000_3000` is reserved and unmapped (M6 kept RGB332) | Absent |
| Framebuffer | `0x3000_0000` | 76,800 bytes | 320×240 pixels, one byte each (M5) | Absent |
| SIMD4 registers | `0x2000_4000` | 32 bytes | Launch/status/entry/counters ([A2](rv32-simd4.md)) | Absent |
| SIMD4 program | `0x2000_5000` | 1,024 bytes | 256 program words | Absent |
| SIMD4 data | `0x2000_6000` | 1,024 bytes | 256 16-bit words in 32-bit CPU slots | Absent |
| Graphics registers | `0x2000_7000` | 128 bytes | Commands/status/counters ([G1](rv32-gfx.md)) | Absent |
| 3D device | `0x2000_8000` | 8 KiB | Registers, constants, shader program, vertex inputs, triangles ([G2](rv32-3d.md)) | Absent |
| RAM | `0x8000_0000` | 4 MiB | Code, data, stack, shared buffers | Only the first 256 KiB: image and `.bss` from `0x8000_0000`; stack `0x8003_C000`–`0x8004_0000` |
| Everything else | — | — | Access fault | Unspecified; QEMU `virt` has other devices there that our firmware never touches |

QEMU runs with `-m 4M` so its RAM bound equals the contract. QEMU stores its device tree near the top of that RAM (2 MiB aligned below the end); firmware ignores it and the 256 KiB slice never reaches it. The timer, input, display, and framebuffer windows were fixed in M5 ([Behavior fixed in M5](#behavior-fixed-in-m5)) and deliberately overlap `virt`'s own devices: its device tree (`-M virt,dumpdtb=`, QEMU 11.1.1) places two 32 MiB flash banks at `0x2000_0000`, the PCIe configuration space at `0x3000_0000`, and PCI memory at `0x4000_0000` to `0x8000_0000`, which covers every device window and the `0x5000_0000` probe address. The diagnostic therefore cannot run on QEMU: after M2 our own emulator is the primary runner, and QEMU compatibility is a goal only for the done register, the console, and RAM.

## Memory transaction contract

For the RTL machine (M3 onward), one ready/valid port per CPU with `addr[31:0]`, `we`, `strb[3:0]`, `wdata[31:0]`, `rdata[31:0]`, and `error`. A request is presented with `valid` and held stable, including all fields, until the slave asserts `ready` in the same cycle. One request is outstanding at a time. `addr` is the byte address of the access and `strb` names its byte lanes within the aligned word, for reads and writes alike: `1111` for a word, `0011` or `1100` for a halfword, one bit for a byte. A write takes effect exactly once, at acceptance, on the strobed lanes only. Reads return the full aligned word; the CPU selects the strobed lanes and sign- or zero-extends bytes and halfwords, and a device uses the strobe to tell a byte read from a wider one (the console status is readable only as the byte at +5). `error` set at acceptance means the access is outside the map or otherwise refused, and the CPU raises the access-fault trap. Devices may hold `ready` low for any number of cycles.

The strobe on reads was fixed in M4: M3's port carried a strobe for writes only, so a byte load of the console status at +5 was the same request as a word load of +4 ([RTL record](rv32-rtl.md#memory-port)). The core also drives a `mem_fetch` sideband that says whether the request is an instruction fetch. Since M5 it is part of the contract: the bus decoder refuses a fetch from any address outside RAM with `error`, so a device never sees a fetch and a jump into a device window is a fetch fault on both backends ([SoC record](rv32-soc.md)).

## Alignment and faults

Only naturally aligned accesses are defined: `lw`/`sw` on 4-byte boundaries, `lh`/`lhu`/`sh` on 2-byte boundaries. Instruction fetch is always 4-byte aligned because there are no compressed instructions. Misaligned data accesses trap in the planned machine; the M1 firmware never performs one. After the done register is written nothing further executes; the startup code spins afterwards only as a guard.

## Behavior fixed in M2

The [emulator](rv32-emulator.md) had to decide everything M1 left undefined. These decisions are now part of the contract and bind the RTL machine too:

- Trap CSRs and instructions: `mtvec`, `mepc`, `mcause`, and `mtval` exist and are accessed with `csrrw`/`csrrs`/`csrrc` and their immediate forms; `mret` sets the PC to `mepc`. No other CSR exists; `mstatus`, `fence.i`, `wfi`, `sret`, and every M-extension encoding are illegal instructions. `mtvec` is direct mode only and `mepc` is word aligned: bits [1:0] of both read as zero. This is the only step beyond bare RV32I, taken because the trap contract cannot be tested without it; `selfcheck` still uses none of it and the image checker still rejects those mnemonics in M1 firmware.
- Trap causes and `mtval` values are tabulated in the emulator document. A trapping instruction has no effect. Misalignment is checked before the address is decoded. Jump and taken-branch targets that are not word aligned trap with `mepc` at the jump and `mtval` holding the target; `jalr` clears bit 0 first.
- Double fault: a trap raised before the handler of the previous trap has retired one instruction stops the machine. With `mtvec` at its reset value 0, the first trap therefore stops the run with a report instead of spinning. QEMU's bare model spins until the driver's timeout.
- Devices: every access the tables below call undefined is an access fault: loads from the console TX register or other console offsets, halfword or word console accesses, stores to the status register, loads from the done register, byte or halfword stores to it. A done word other than pass, fail with code 1..255, or the reserved reset word is an emulator error; the reset word is also an error and never resets.
- RAM is 4 MiB; the 256 KiB slice is a constraint on the M1 image, not on the machine. Registers other than the PC reset to zero in the emulator, but firmware may not rely on it.

## Behavior fixed in M4

The [RTL core](rv32-rtl.md) now executes all of RV32I plus the M2 trap subset, and the decisions below make its trace equal the emulator's in every case:

- Reads carry the strobe (above). The retirement trace shows a load's raw strobed lanes before extension, the same bytes the emulator prints, so `lb`, `lh`, `lbu`, `lhu`, and `sh` are compared like `lw` and `sw`.
- Traps vector on the RTL as on the emulator: `mepc` is the trapping instruction's PC (the fetch address for a fetch fault), `mcause` and `mtval` as tabulated in the emulator document, and execution continues at `mtvec`. The trapping instruction has no effect: a load or store that the port refuses was presented on the bus and accepted with `error`, but writes nothing.
- The double-fault rule from M2 binds the RTL: a trap raised before the handler of the previous trap has retired one instruction halts the core, and both backends report `double-fault`. With `mtvec` at its reset value the first trap is followed by the fetch fault at address 0, then the halt; both trap lines appear in both traces.
- CSR accesses: `csrrw` always writes; `csrrs` and `csrrc` (and their immediate forms) write only when the `rs1` field is nonzero; `rd` receives the old value; `mtvec` and `mepc` keep bits [1:0] zero. The CSR write and the register write commit together at retirement. `mret` sets the PC to `mepc`. `fence` with `funct3` 0 retires with no effect whatever its other fields.

## Behavior fixed in M5

M5 gave the machine its devices, as RTL peripherals behind a bus decoder and as matched emulator models ([SoC record](rv32-soc.md), [emulator record](rv32-emulator.md)). The decisions below bind both backends:

- The windows in the memory map above. Inside a window, every offset, width, and direction the device tables below do not list is an access fault with `mtval` holding the effective address, exactly as for the console and done register since M2. Misalignment is still checked before the address is decoded.
- The bus refuses instruction fetches outside RAM (`mem_fetch` above), so the only way to execute a device register is a fetch fault.
- Device time: timer values and A2/G1 accelerator completion/status/counters depend on the backend's tick rate. Programs using neither timer reads nor asynchronous accelerator registers retain one retirement trace, compared line for line as in M4. Programs using these timing interfaces are compared at the results level: console transcript, halt outcome, checkpoint list, and ordered trap records (PC, word, cause and value, excluding step numbers). The A2 diagnostic additionally checks ordered stores with `--compare-stores`; this is opt-in because firmware can store timing-dependent values even without reading the timer. See [Device time](#device-time) and [A2](rv32-simd4.md).
- Reset: the timer, the input queue and held-key mask, and the frame count reset to zero. RAM and framebuffer contents are unspecified after a reset; both backends start a run with them zero-filled.
- The RTL's console may hold `ready` low for a configurable number of cycles per byte (the contract already allows any device to); the emulator never waits. Firmware still polls the status byte before each store.

## Behavior fixed in M6

M6 gave the emulator a native window and the machine its first game ([window record](rv32-window.md)). Nothing in the RTL changed; the decisions below concern the host side and are what a recorded session relies on:

- Host keys become events at presents. The window collects the keys typed since the previous present and queues them, in order, as events of the frame the next present raises, at the same point a script's events for that frame arrive. A key press is one event however long it is held (the host ignores key repeats), a release is one event, and an unmapped key is nothing. The host's map is LEFT, RIGHT, UP, DOWN, SPACE, RETURN (the contract's ENTER), ESCAPE, A, D, W, S, P, Q, R.
- A recording is a script. With `--record`, both hosts write every event offered to the queue, scripted or typed, as a `frame N down|up KEY` line before the queue decides whether to hold it, so replaying the recording reproduces the run including its drops. Frame 0's scripted events are recorded at frame 0; keys typed before the first present are recorded at frame 1.
- Time enters only through pacing. The window shows at most `--fps` presents a second (60 by default) by sleeping between them; the timer stays an instruction counter in every mode, and there is no host-time timer mode. A program that paces itself on presents, as Pong does, therefore replays identically on the window, the headless emulator, and the RTL, and keeps the trace-identical comparison.
- A host may stop the run. Closing the window halts the machine with `halt=stopped` (`error=host-stopped`, exit status 2); the guest's own outcomes are unchanged.
- The pixel mapping stays RGB332 and the palette window stays reserved and unmapped: an access there is a fault on both backends, as in M5.

## Devices

### Console at `0x1000_0000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Write byte | Transmit the byte |
| +5 | Read byte | Bit 5 (`0x20`) set when a byte can be accepted; other bits read 0 |

In our machine the ready bit is always 1 and every byte is accepted immediately. Firmware still polls it before each store so the same image behaves on a real UART: on QEMU this is the 16550's transmit-holding and line-status registers, which never block here either. Reads from +0 and every other offset, and every non-byte access, are access faults (fixed in M2). Output is bytes; the firmware chooses the text.

### Done register at `0x0010_0000`

| Word written | Meaning | QEMU exit status |
| --- | --- | --- |
| `0x0000_5555` | Pass | 0 |
| `(code << 16) \| 0x3333`, code 1..255 | Fail with `code` | `code` |
| `0x0000_7777` | Reserved: QEMU resets the machine; never write it (we run with `-no-reboot`) | — |
| Anything else | Emulator error (fixed in M2) | — |
| Byte/halfword writes, any read | Access fault (fixed in M2) | — |

Codes are limited to 1..255 because process exit statuses are eight bits; a larger code would be truncated and code 0 would be indistinguishable from pass. The M1 firmware prints exactly one console line before the write: `PASS <8 hex digits>` or `FAIL <code>`. The driver requires the line and the exit status to agree. The M5 diagnostic prints several lines and ends with the same `PASS`/`FAIL` line; its runner checks the last line and compares the whole transcript between backends.

### Timer at `0x2000_0000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Read word | `TICKS`: the current tick count |
| +0 | Write word | Load the tick count; counting continues from the written value |

`TICKS` is a free-running 32-bit counter that wraps to zero. Offsets +4 to +12 and every byte or halfword access fault. What one tick is depends on the backend ([Device time](#device-time)), so firmware may rely only on the count increasing modulo 2^32 (measure intervals with unsigned subtraction) and never on its rate. There are no interrupts: waiting is polling.

### Input at `0x2000_1000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Read word | `EVENT`: remove and return the oldest queued event, or 0 when the queue is empty |
| +4 | Read word | `COUNT`: events currently queued, 0 to 16 |
| +8 | Read word | `KEYS`: bit `k` set while key code `k` is held |

Every write and every byte or halfword access faults. An event word is `0` (none) or `0x8000_0000 | (press << 8) | code`: bit 31 marks a valid event, bit 8 is 1 for a press and 0 for a release, bits 4:0 hold the key code, and bits 30:9 and 7:5 are zero. Key codes are 0..31 so that `KEYS` can hold one bit per key; the named codes are in [board.h](../programs/rv32/board.h) (`LEFT` 1, `RIGHT` 2, `UP` 3, `DOWN` 4, `SPACE` 5, `ENTER` 6, `ESCAPE` 7, then letters), and the native window maps host keys to them ([Behavior fixed in M6](#behavior-fixed-in-m6)). `KEYS` changes when an event *arrives* in the queue, not when firmware pops it, so it reflects the host's keyboard state; a press and a release that arrive together leave the bit clear even before the events are read. The queue holds 16 events; the host drops an event that arrives when it is full and reports the drop on its diagnostic stream.

Where events come from: the host is a script on both backends, or the keyboard in the window (M6) (`frame N down KEY` and `frame N up KEY` lines, non-decreasing `N`, `KEY` a name from `board.h` or a number 0..31; a number is one to nine ASCII digits; a line whose first token begins with `#` is a comment, and trailing comments are not allowed). An event scheduled for frame `N` arrives in the queue when the present store that raises the frame count to `N` retires; frame 0 events are queued before the first instruction. Events with the same frame arrive in script order. Tying arrival to a guest-observable checkpoint rather than to a tick count is what makes the sequence identical on both backends. An event the script scheduled and the program never saw, because the queue was full or the frame was never presented, is reported after the halt line and turns a passing run into a failure (a nonzero exit status on both backends) unless the host was told to expect it (`--allow-lost-events`, `+allow-lost-events`): the guest's pass says nothing about events it never received. A guest that failed or was halted keeps its own outcome, since a firmware that stops early naturally leaves later events unread.

### Display at `0x2000_2000` and framebuffer at `0x3000_0000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Write word | `PRESENT`: present the framebuffer; faults while G1 is BUSY; the value is ignored |
| +4 | Read word | `FRAMES`: presents since reset |
| +8 | Read word | `WIDTH`: 320 |
| +12 | Read word | `HEIGHT`: 240 |

Reads of +0, writes to +4 to +12, and every byte or halfword access fault. The framebuffer window is 76,800 bytes of ordinary memory: one 8-bit pixel per byte, row-major from the top-left pixel, `WIDTH` bytes per row, readable and writable as bytes, halfwords, and words while G1 is not BUSY (CPU accesses fault during ownership); the byte after the last pixel faults. Its contents are unspecified at reset. A store to it is data movement and nothing else: nothing is visible until a present, when the backend takes a snapshot of the whole window. The snapshot becomes a checkpoint line `frame N <8 hex digits>` (the hash below) on every backend, and the native window shows it (M6). The pixel value is a color index with a fixed mapping, bits 7:5 red, 4:2 green, 1:0 blue (RGB332), each field scaled to full range (`r = field × 255 / 7`, `b = field × 255 / 3`); a palette was considered in M6 and deferred, and its window stays reserved.

The checkpoint hash covers pixel bytes only, in address order, as the 19,200 little-endian words of the window: `h = ((h << 5) + h) ^ word` starting from `h = 5381`, 32-bit arithmetic, printed as eight lowercase hex digits. It uses shifts and adds only because RV32I has no multiply instruction and the firmware computes the same hash over a frame it reads back; a palette added later never changes a recorded checkpoint.

### Device time

The emulator executes one instruction per loop iteration and knows nothing about clocks; the RTL takes 4 or 5 cycles per instruction plus stalls. A tick is therefore backend-specific:

| Backend | One tick | Origin | What a read returns |
| --- | --- | --- | --- |
| RTL | One clock cycle | The first rising edge after reset release is cycle 1 | The count in the cycle the bus accepts the read: a `lw` accepted in cycle `k` reads `k` |
| Emulator (every mode) | One executed instruction (retired or trapped) | The first instruction is step 1 | The count before the reading instruction: a load inside instruction `N` reads `N − 1` |

A written value replaces the count and the rate continues. M6 decided against a host-time mode: the window paces presents instead, and the timer counts instructions in every mode, so a session recorded in the window replays exactly on every backend. Input arrival is keyed to frames; presents and checkpoints happen at the accepting store, console bytes and the done word at their stores. A2 adds an autonomous accelerator: it advances once per RTL clock or emulated CPU instruction (including traps), with STATUS and counters observed before the accepting emulator instruction's tick. Emulator accelerator STALLS is always zero; RTL test inputs may delay transfers. Timer waits and accelerator polling therefore use result-level comparison rather than identical CPU traces.

## Firmware image and ABI

The image is an ELF32 little-endian executable: `e_machine` 243 (RISC-V), `e_type` `ET_EXEC`, `e_flags` 0 (no compressed instructions, soft-float ABI), `Tag_RISCV_arch` `rv32i2p1`. One `PT_LOAD` segment starts at `0x8000_0000` with load address equal to run address, so startup copies nothing. Section order and symbols come from [link.ld](../programs/rv32/link.ld):

| Section or symbol | Meaning |
| --- | --- |
| `.text` | Code; `.text.init` from [start.S](../programs/rv32/start.S) is kept first so `_start` is at `0x8000_0000` |
| `.rodata` | Constants and string literals |
| `.data`, `__data_start`, `__data_end` | Initialized globals, already in place when loaded |
| `.bss`, `__bss_start`, `__bss_end` | Zero-initialized globals, word aligned, zeroed by `_start` |
| `_end` | First free byte after `.bss` |
| `_stack_bottom`, `_stack_top` | 16 KiB stack at the top of the 256 KiB slice; `_stack_top` is 16-byte aligned |

Startup sets `sp`, zeroes `.bss` one word at a time, calls `main`, then falls into `rv32_exit`, which converts `main`'s return value (0 pass, 1..255 fail) into the done word. No global pointer is set up because linker relaxation is disabled; no thread pointer or heap exists.

Compiler and linker flags, from the [Makefile](../Makefile):

| Flag | Reason |
| --- | --- |
| `--target=riscv32-unknown-elf -march=rv32i -mabi=ilp32` | Base ISA only; soft-float ILP32 objects |
| `-mcmodel=medlow` | Absolute `lui`/`addi` addressing; on RV32 it spans the whole address space, so `0x8000_0000` is fine and linked addresses are visible in listings |
| `-mno-relax` | The linker leaves instruction sequences as compiled, so object and linked listings match line for line; enabling relaxation is an exercise |
| `-ffreestanding -fno-builtin -nostdlib -static` | No hosted C library, no implicit calls except the arithmetic libcalls we supply |
| `-O2 -g` | Real code generation with source interleaved in the listing |
| `-fno-asynchronous-unwind-tables -fno-unwind-tables` | No `.eh_frame`; the image checker rejects unexpected allocated sections |
| `--ld-path=/opt/homebrew/opt/lld/bin/ld.lld` | Explicit linker; `-fuse-ld=lld` would search the compiler's own directory and then `PATH` |

### Runtime routines

Clang lowers 32-bit `*`, `/`, and `%` on an RV32I target to calls named `__mulsi3`, `__divsi3`, `__udivsi3`, `__modsi3`, and `__umodsi3`. Homebrew's LLVM ships no compiler-rt for RISC-V, so [muldiv.c](../programs/rv32/rt/muldiv.c) provides them as aliases of `rv32_mul`, `rv32_div`, `rv32_divu`, `rv32_rem`, and `rv32_remu`. Results follow the RISC-V M extension exactly: division by zero yields all ones (`-1`) with the dividend as remainder; `INT32_MIN / -1` yields `INT32_MIN` with remainder 0; signed quotients truncate toward zero. Future `MUL`/`DIV`/`REM` hardware must agree with these routines. The same file compiles natively so [test_rv32_rt.py](../tests/test_rv32_rt.py) can compare it with Python integers at `-O0` and `-O2`.

The signed routines work on unsigned magnitudes and fix up the sign afterwards, so `INT32_MIN` is never negated as a signed value.

### Image outputs and checks

`make firmware-rv32` writes `build/rv32/selfcheck.elf`, `.lst` (disassembly with source), `.bin` (flat image from `0x8000_0000`), `.map`, and `.readelf`, and since M5 the same five files for `diag`, the device diagnostic ([record](rv32-soc.md#the-diagnostic)), which links [trap.S](../programs/rv32/trap.S) as well. `make check-rv32-image` runs [rv32_image.py](../tools/rv32_image.py), a standard-library ELF32 parser whose flattened `.bin` is what the emulator loads. It rejects an image unless: class, byte order, machine, type, and `e_flags` match the contract; the entry point, `_start`, and the lowest load address are all `0x8000_0000`; every load segment is word aligned, has equal load/run addresses, and lies inside the 256 KiB slice; `.text`, `.rodata`, `.data`, `.bss` exist and no other allocated section does; the `.bss` symbols match the section; the stack follows `_end` inside RAM with a 16-byte aligned top; no symbol is undefined; the listing contains no undecodable instruction and no `mul*`, `div*`, `rem*`, `csr*`, `c.*`, `fence.i`, `ecall`, `ebreak`, `wfi`, or `*ret`. The diagnostic is checked with `--allow-privileged`, which admits `csr*` and `mret` for its trap handler and nothing else. It also writes `build/rv32/selfcheck.hex`, little-endian 32-bit words from `0x8000_0000` for `$readmemh`, and verifies the `.bin` written by `llvm-objcopy` equals its own flattening byte for byte.

```sh
make run-rv32-qemu      # Run the self-check on QEMU virt; save the console transcript; compare exit status

make run-rv32-pong      # Pong in the window, recording the session (M6); run-rv32-pong-emu replays the scripted session

make disasm-rv32        # Print the self-check listing (disasm-rv32-diag, disasm-rv32-pong, disasm-rv32-capstone: the others')
```

`make test` remains the counter test and every earlier target is unchanged. Tool locations are Make variables with defaults for Homebrew on Apple Silicon: `RV32_LLVM` (`/opt/homebrew/opt/llvm@22/bin`), `RV32_LD` (`/opt/homebrew/opt/lld/bin/ld.lld`), `QEMU_RV32` (`qemu-system-riscv32`). Install with `brew install llvm@22 lld qemu`; the compiler and linker come from different LLVM releases (22.1.8 and 23.1.1), which is fine for static RISC-V ELF linking. Nothing needs to be on `PATH`.

To run by hand:

```sh
qemu-system-riscv32 -M virt -cpu rv32i -bios none -kernel build/rv32/selfcheck.elf \
```

`tools/rv32_run_qemu.py --cpu` accepts alternatives if a future QEMU release stops booting the bare model: `rv32i,zicsr=true`, then `rv32,m=false,a=false,f=false,d=false,c=false`.

## Behavior fixed in M7

The [runtime/menu/Tetris contract](rv32-runtime.md) adds a combined guest
firmware image without changing the ISA, MMIO map, input encoding, timer,
framebuffer or host frontend. Both games advance on presented frames; the
seeded seven-bag never reads the timer. Menu transitions consume the current
event batch except session-level Q, and block held launch controls until release. Static memory and
the existing 16 KiB stack suffice; no allocator or privileged services were
added. `make run-rv32-capstone` builds and launches the menu and both games.


## Behavior fixed in F2

The machine now supports RV32IF with Zicsr, retaining the existing minimal
trap environment. The [F2 architectural contract](rv32-f.md) fixes all floating
instructions/state, CSR aliases, reserved-mode traps, reset cancellation,
retirement effects and compiler ISA/ILP32 flags. Floating state is always enabled;
this does not add privileged FS state or context switching. FLW/FSW use the
existing aligned word memory and device rules. Integer firmware remains RV32I.

## Behavior fixed in A2

The SIMD4 command/status window at `0x20004000`, program window at `0x20005000`,
and data-slot window at `0x20006000` follow the [A2 device contract](rv32-simd4.md).
The CPU transfers ownership of both private memories to the engine at START
and regains it at completion or reset. These windows are not QEMU devices.

## Behavior fixed in G1

The [G1 contract](rv32-gfx.md) fixes fill/blit/line/triangle coverage, the graphics
registers, clipping, overlapping copies, and reset. The device owns the framebuffer
while BUSY: CPU framebuffer access and PRESENT fault. RAM-source blits also protect
the complete source extent from CPU writes while allowing reads/fetches and unrelated
writes. The RTL arbitrates RAM reads fairly; this is the machine's first accelerator
path to ordinary RAM and framebuffer memory. A2's private SIMD4 windows are unchanged.

Graphics status and counters are asynchronous like A2. Comparison uses observable
results/checkpoints/trap order; timing-dependent instruction traces and stores need
not match. FENCE remains an ordering no-op on this uncached machine: it does not
wait for accelerator completion. Poll DONE before reading or presenting pixels.
