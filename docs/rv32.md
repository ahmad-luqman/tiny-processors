# RV32 machine: contract and first firmware

This document fixes the machine contract for our RISC-V computer and describes the first firmware image built against it. It is our own small machine, not a Linux-capable platform and not a copy of QEMU's `virt` board: three addresses were chosen to coincide with `virt` so QEMU can serve as an independent reference runner, nothing else is borrowed. SAP8 remains the separate teaching CPU.

Primary sources: the [RV32I chapter](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html) of the RISC-V unprivileged specification (RV32I version 2.1) and the [RISC-V ELF psABI](https://github.com/riscv-non-isa/riscv-elf-psabi-doc) (integer calling convention, `e_flags`).

## Implementation plan (M1)

1. Record actual tool paths and versions; read the ISA chapter and psABI before fixing the contract.
2. Write the contract below: reset, byte order, address map, memory transactions, alignment and faults, supported ISA, and the console/done protocol.
3. Complete the cross toolchain: Homebrew Clang 22 compiles RV32I, Homebrew lld links it, QEMU runs it.
4. Add startup assembly, a linker script, the multiply/divide runtime, and a C self-check with hand-computed expected values.
5. Execute the image on QEMU and require the console line and exit status to agree.
6. Add build/validation commands without touching the default counter target; write the [C-to-instructions walkthrough](c-to-instructions.md).

All six steps are complete; see [Milestone result](#milestone-result).

## Supported ISA and privilege

- RV32I version 2.1: 32 registers with `x0` hardwired to zero, 32-bit instructions only. No M, A, F, D, or C extensions. Multiplication and division are runtime routines.
- ILP32 soft-float C ABI: `int`, `long`, and pointers are 4 bytes; arguments in `a0`–`a7`, results in `a0`/`a1`; `s0`–`s11` callee-saved; `sp` 16-byte aligned at every call; integers narrower than 32 bits are widened according to their own signedness.
- Little-endian memory. `FENCE` completes with no effect: one hart, no caches.
- Planned machine: machine mode only, until Track 2 added user mode and PMP ([O5](#o5-protection)) and issue #20 supervisor mode and Sv32 ([Sv32](#s-mode-and-sv32-issue-20)). `ECALL`, `EBREAK`, illegal instructions, misaligned accesses, and accesses outside the map trap through `mtvec` with `mcause`/`mepc`/`mtval` (or, delegated since issue #20, through `stvec` with `scause`/`sepc`/`stval`); interrupts arrived with Track 2 ([O1](#o1-interrupts)), which also made `mstatus`, `mie`, `mip`, `mscratch` and `wfi` legal. The emulator (M2) implements this trap contract; see [Behavior fixed in M2](#behavior-fixed-in-m2).
- M1 slice: no CSR instructions are used or required. There is no trap handler; a trap on the reference runner vectors to the reset value of `mtvec`, address 0, which has no memory, so the run hangs and the driver reports a timeout. This is a recorded limitation, not an accepted behavior.

## Reset

At reset the PC is `0x8000_0000`. Since Track 1, `a0` holds the hart id (0) and `a1` the address of a flattened device tree describing the platform ([Boot convention](#boot-convention)); every other register is unspecified, so firmware must not read one before writing it. Memory holds the firmware image at its link addresses; other RAM contents are unspecified and `.bss` is zeroed by startup code.

QEMU reconciliation: `qemu-system-riscv32 -M virt -cpu rv32i -bios none -kernel image.elf` runs a mask ROM at `0x1000` that loads `a1` with a device-tree pointer, would load `a0` with the hart id (a `csrr`, executed as `nop` on the CSR-less `rv32i` model), and jumps to the DRAM base `0x8000_0000`. This was verified with `-d in_asm`. Our image therefore does not rely on the ELF loader honoring `e_entry`: the build asserts `e_entry == _start == lowest load address == 0x8000_0000`, and `_start` is the first instruction of the image. Since Track 1 the platform check runs with `-cpu rv32` instead (QEMU 8.2 has no bare `rv32i` model): there the `csrr` executes, `a0` is 0, and [start.S](../programs/rv32/start.S) passes both registers to `main` untouched ([Boot convention](#boot-convention)).

QEMU runs with `-m 4M` so its RAM bound equals the contract. QEMU stores its device tree near the top of that RAM (2 MiB aligned below the end); firmware ignores it and the 256 KiB slice never reaches it. The timer, input, display, and framebuffer windows were fixed in M5 ([Behavior fixed in M5](#behavior-fixed-in-m5)) at `0x2000_0000` and `0x3000_0000`, and the accelerators joined them at `0x2000_4000`–`0x2000_9fff`; those windows overlapped `virt`'s own devices (two 32 MiB flash banks at `0x2000_0000`, the PCIe configuration space at `0x3000_0000`). Track 1 moved every register window to `0x1100_xxxx` (same low offsets) and the framebuffer to `0x1200_0000`, in the hole `virt` leaves between its `fw_cfg` at `0x1010_0000` and its flash, and replaced the timer with a CLINT at `virt`'s address. `make check-rv32-virt-map` checks the result against QEMU's own tree: every shared device matches, every other window is disjoint from everything `virt` describes, so touching one of our devices on QEMU is an access fault rather than a read of flash. Records written before Track 1 quote the old addresses. The diagnostic still cannot run on QEMU, since our devices do not exist there; [platcheck](rv32-platform.md) runs on all three backends and uses our devices only where the device tree lists them. The `0x5000_0000` probe address stays unmapped on our machine (it is PCI memory on `virt`).

## Memory transaction contract

For the RTL machine (M3 onward), one ready/valid port per CPU with `addr[31:0]`, `we`, `strb[3:0]`, `wdata[31:0]`, `rdata[31:0]`, and `error`. A request is presented with `valid` and held stable, including all fields, until the slave asserts `ready` in the same cycle. One request is outstanding at a time. `addr` is the byte address of the access and `strb` names its byte lanes within the aligned word, for reads and writes alike: `1111` for a word, `0011` or `1100` for a halfword, one bit for a byte. A write takes effect exactly once, at acceptance, on the strobed lanes only. Reads return the full aligned word; the CPU selects the strobed lanes and sign- or zero-extends bytes and halfwords, and a device uses the strobe to tell a byte read from a wider one (the console status is readable only as the byte at +5). `error` set at acceptance means the access is outside the map or otherwise refused, and the CPU raises the access-fault trap. Devices may hold `ready` low for any number of cycles.

The strobe on reads was fixed in M4: M3's port carried a strobe for writes only, so a byte load of the console status at +5 was the same request as a word load of +4 ([RTL record](rv32-rtl.md#memory-port)). The core also drives a `mem_fetch` sideband that says whether the request is an instruction fetch. Since M5 it is part of the contract: the bus decoder refuses a fetch from any address outside RAM with `error`, so a device never sees a fetch and a jump into a device window is a fetch fault on both backends ([SoC record](rv32-soc.md)).

## Alignment and faults

Only naturally aligned accesses are defined: `lw`/`sw` on 4-byte boundaries, `lh`/`lhu`/`sh` on 2-byte boundaries. Instruction fetch is always 4-byte aligned because there are no compressed instructions. Misaligned data accesses trap in the planned machine; the M1 firmware never performs one. After the done register is written nothing further executes; the startup code spins afterwards only as a guard.

## Behavior fixed in M2

The [emulator](rv32-emulator.md) had to decide everything M1 left undefined. These decisions are now part of the contract and bind the RTL machine too:

- Trap CSRs and instructions: `mtvec`, `mepc`, `mcause`, and `mtval` exist and are accessed with `csrrw`/`csrrs`/`csrrc` and their immediate forms; `mret` sets the PC to `mepc`. No other CSR exists; `mstatus`, `fence.i`, `wfi`, `sret`, and every M-extension encoding are illegal instructions. `mtvec` is direct mode only and `mepc` is word aligned: bits [1:0] of both read as zero. This is the only step beyond bare RV32I, taken because the trap contract cannot be tested without it; `selfcheck` still uses none of it and the image checker still rejects those mnemonics in M1 firmware.
- Trap causes and `mtval` values are tabulated in the emulator document. A trapping instruction has no effect. Misalignment is checked before the address is decoded. Jump and taken-branch targets that are not word aligned trap with `mepc` at the jump and `mtval` holding the target; `jalr` clears bit 0 first.
- Double fault: a trap raised before the handler of the previous trap has retired one instruction stops the machine. With `mtvec` at its reset value 0, the first trap therefore stops the run with a report instead of spinning. QEMU's bare model spins until the driver's timeout.
- Devices: every access the tables below call undefined is an access fault: loads from the console TX register or other console offsets, halfword or word console accesses, stores to the status register, loads from the done register, byte or halfword stores to it. A done word other than pass, fail with code 1..255, or the reserved reset word is an emulator error; the reset word is also an error and never resets.
- RAM is 4 MiB; the 256 KiB slice is a constraint on the M1 image, not on the machine. Registers other than the PC reset to zero in the emulator, but firmware may not rely on it.

## Behavior fixed in M4

The [RTL core](rv32-rtl.md) now executes all of RV32I plus the M2 trap subset, and the decisions below make its trace equal the emulator's in every case:

- Reads carry the strobe (above). The retirement trace shows a load's raw strobed lanes before extension, the same bytes the emulator prints, so `lb`, `lh`, `lbu`, `lhu`, and `sh` are compared like `lw` and `sw`.
- Traps vector on the RTL as on the emulator: `mepc` is the trapping instruction's PC (the fetch address for a fetch fault), `mcause` and `mtval` as tabulated in the emulator document, and execution continues at `mtvec`. The trapping instruction has no effect: a load or store that the port refuses was presented on the bus and accepted with `error`, but writes nothing.
- The double-fault rule from M2 binds the RTL: a trap raised before the handler of the previous trap has retired one instruction halts the core, and both backends report `double-fault`. With `mtvec` at its reset value the first trap is followed by the fetch fault at address 0, then the halt; both trap lines appear in both traces.
- CSR accesses: `csrrw` always writes; `csrrs` and `csrrc` (and their immediate forms) write only when the `rs1` field is nonzero; `rd` receives the old value; `mtvec` and `mepc` keep bits [1:0] zero. The CSR write and the register write commit together at retirement. `mret` sets the PC to `mepc`. `fence` with `funct3` 0 retires with no effect whatever its other fields.

## Behavior fixed in M5

M5 gave the machine its devices, as RTL peripherals behind a bus decoder and as matched emulator models ([SoC record](rv32-soc.md), [emulator record](rv32-emulator.md)). The decisions below bind both backends:

- The windows in the memory map above. Inside a window, every offset, width, and direction the device tables below do not list is an access fault with `mtval` holding the effective address, exactly as for the console and done register since M2. Misalignment is still checked before the address is decoded.
- The bus refuses instruction fetches outside RAM (`mem_fetch` above), so the only way to execute a device register is a fetch fault.
- Device time: timer values and A2/G1 accelerator completion/status/counters depend on the backend's tick rate. Programs using neither timer reads nor asynchronous accelerator registers retain one retirement trace, compared line for line as in M4. Programs using these timing interfaces are compared at the results level: console transcript, halt outcome, checkpoint list, and ordered trap records (PC, word, cause and value, excluding step numbers). The A2 diagnostic additionally checks ordered stores with `--compare-stores`; this is opt-in because firmware can store timing-dependent values even without reading the timer. See [Device time](#device-time) and [A2](rv32-simd4.md).
- Reset: the timer, the input queue and held-key mask, and the frame count reset to zero. RAM and framebuffer contents are unspecified after a reset; both backends start a run with them zero-filled.
- The RTL's console may hold `ready` low for a configurable number of cycles per byte (the contract already allows any device to); the emulator never waits. Firmware still polls the status byte before each store.

## Behavior fixed in M6

M6 gave the emulator a native window and the machine its first game ([window record](rv32-window.md)). Nothing in the RTL changed; the decisions below concern the host side and are what a recorded session relies on:

- Host keys become events at presents. The window collects the keys typed since the previous present and queues them, in order, as events of the frame the next present raises, at the same point a script's events for that frame arrive. A key press is one event however long it is held (the host ignores key repeats), a release is one event, and an unmapped key is nothing. The host's map is LEFT, RIGHT, UP, DOWN, SPACE, RETURN (the contract's ENTER), ESCAPE, A, D, W, S, P, Q, R.
- A recording is a script. With `--record`, both hosts write every event offered to the queue, scripted or typed, as a `frame N down|up KEY` line before the queue decides whether to hold it, so replaying the recording reproduces the run including its drops. Frame 0's scripted events are recorded at frame 0; keys typed before the first present are recorded at frame 1.
- Time enters only through pacing. The window shows at most `--fps` presents a second (60 by default) by sleeping between them; the timer stays an instruction counter in every mode, and there is no host-time timer mode. A program that paces itself on presents, as Pong does, therefore replays identically on the window, the headless emulator, and the RTL, and keeps the trace-identical comparison.
- A host may stop the run. Closing the window halts the machine with `halt=stopped` (`error=host-stopped`, exit status 2); the guest's own outcomes are unchanged.
- The pixel mapping stays RGB332 and the palette window stays reserved and unmapped: an access there is a fault on both backends, as in M5.

## Devices

### Console at `0x1000_0000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Write byte | Transmit the byte |
| +0 | Read byte | RBR (O2): take the next received byte; 0 when none is waiting |
| +5 | Read byte | Bit 5 (`0x20`) set when a byte can be accepted; bit 0 (O2) set while a received byte waits; other bits read 0 |

In our machine the ready bit is always 1 and every byte is accepted immediately. Firmware still polls it before each store so the same image behaves on a real UART: on QEMU this is the 16550's transmit-holding and line-status registers, which never block here either. Every other offset and every non-byte access is an access fault (fixed in M2). Output is bytes; the firmware chooses the text.

The receive side arrived with Track 2's O2, for the shell: the host gives the console a file of bytes (`--console-input` on the emulator, `+console-input=` on the testbench, stdin on QEMU), every one of them waiting from reset, so a scripted session is the same on every backend; `--console-input -` gives the emulator stdin as it arrives, for interactive use. Before O2 a read of +0 faulted. The console raises no interrupt (a 16550's IER is not implemented), so software polls bit 0.

### Done register at `0x0010_0000`

| Word written | Meaning | QEMU exit status |
| --- | --- | --- |
| `0x0000_5555` | Pass | 0 |
| `(code << 16) \| 0x3333`, code 1..255 | Fail with `code` | `code` |
| `0x0000_7777` | Reserved: QEMU resets the machine; never write it (we run with `-no-reboot`) | — |
| Anything else | Emulator error (fixed in M2) | — |
| Byte/halfword writes, any read | Access fault (fixed in M2) | — |

Codes are limited to 1..255 because process exit statuses are eight bits; a larger code would be truncated and code 0 would be indistinguishable from pass. The M1 firmware prints exactly one console line before the write: `PASS <8 hex digits>` or `FAIL <code>`. The driver requires the line and the exit status to agree. The M5 diagnostic prints several lines and ends with the same `PASS`/`FAIL` line; its runner checks the last line and compares the whole transcript between backends.

### CLINT at `0x0200_0000`

Track 1 replaced the M5 timer (`TICKS` at `0x2000_0000`) with the core-local interruptor of QEMU's `virt` board, for one hart:

| Offset | Access | Meaning |
| --- | --- | --- |
| +`0x0000` | Read/write word | `msip`: bit 0 holds what is written, other bits read 0 |
| +`0x4000`, +`0x4004` | Read/write word | `mtimecmp` low and high words; all ones at reset |
| +`0xbff8`, +`0xbffc` | Read/write word | `mtime` low and high words: the current tick count |

`mtime` is a free-running 64-bit counter; a write to one half replaces that half of the current count and counting continues from there, exactly as a `TICKS` write did (so the low word behaves as `TICKS` did, and carries into the high word). Every other offset in the 64 KiB window and every byte or halfword access faults. What one tick is depends on the backend ([Device time](#device-time)); on QEMU it is 100 ns of host time, or of instruction-counted virtual time (8 ns an instruction) in the OS sessions, which run with `-icount` ([docs/rv32-os.md](rv32-os.md)). The Zicntr `time` CSR reads `mtime`. Since O1, `mip.MTIP` is `mtime >= mtimecmp` and `mip.MSIP` is `msip`, so both raise interrupts ([Behavior fixed in Track 2](#behavior-fixed-in-track-2)).

### PLIC at `0x0c00_0000`

The platform-level interrupt controller of QEMU's `virt` board (Track 2, O1), in its SiFive register layout, for one context: hart 0 in machine mode. Word access only; every other offset in the 6 MiB window and every byte or halfword access faults.

| Offset | Access | Meaning |
| --- | --- | --- |
| +`4 × n`, n = 1..31 | Read/write word | Source n's priority, 3 bits; +0 (source 0) reads 0 |
| +`0x1000` | Read word | Pending: bit n set by source n's gateway (below), cleared by a claim |
| +`0x2000` | Read/write word | Context 0's enables, one bit per source |
| +`0x20_0000` | Read/write word | Context 0's threshold, 3 bits |
| +`0x20_0004` | Read: claim; write: complete | A read returns the pending, enabled source with the highest priority above the threshold (ties to the lowest number), or 0, clears its pending bit and marks it claimed; writing its number back while it is enabled completes it |

Only wired sources hold a priority or an enable; the others read 0 and ignore writes. Each wired source has a gateway, as the PLIC specification describes and QEMU implements: while the source is not claimed, its line being high sets its pending bit, and the bit then stays set whatever the line does, until a claim clears it; after a completion a line still high sets it again. (The RTL's gateways sample every clock, the emulator's before every step; a line changes only through a device access or an input event, so both see the same requests. Until PR #19's review the pending bit followed the line, which QEMU 8's PLIC also did and QEMU 11's does not.) `mip.MEIP` is set while a claim would return nonzero. Wired: source 1 is virtio-blk (its `InterruptStatus` nonzero, O3) and source 12 the input queue (its line is `COUNT` nonzero).

### virtio-blk at `0x1000_1000`

A block device in the register layout of virtio-mmio version 2 (the virtio 1.x specification, "Virtio Over MMIO"), at `virt`'s first virtio slot, so the same driver serves QEMU's (started with `-global virtio-mmio.force-legacy=false` and the drive on `virtio-mmio-bus.0`). Word access only; an offset not in the table, a write to a read-only register, a read of a write-only one and every byte or halfword access fault.

| Offset | Access | Meaning |
| --- | --- | --- |
| +`0x000`, `0x004`, `0x008`, `0x00c` | Read | MagicValue `0x7472_6976` ("virt"), Version 2, DeviceID 2 (block), VendorID `0x594e_4954` |
| +`0x010`, +`0x014` | Read, write | DeviceFeatures of the word DeviceFeaturesSel chooses: word 1 bit 0 (`VIRTIO_F_VERSION_1`), nothing else |
| +`0x020`, +`0x024` | Write | DriverFeatures, DriverFeaturesSel: accepted, not checked |
| +`0x030`, `0x034`, `0x038`, `0x044` | Write, read, write, read/write | QueueSel, QueueNumMax (8 for queue 0, else 0), QueueNum (1, 2, 4 or 8; anything else is 0), QueueReady |
| +`0x050` | Write | QueueNotify: see below |
| +`0x060`, `0x064` | Read, write | InterruptStatus (bit 0: a used buffer), InterruptACK |
| +`0x070` | Read/write | Status; writing 0 resets the device (the queue, its indices and the interrupt), not the disk |
| +`0x080`–`0x0a4` | Read/write | QueueDesc, QueueDriver, QueueDevice, low and high words |
| +`0x0fc`, `0x100`, `0x104` | Read | ConfigGeneration 0; capacity in 512-byte sectors, 256 (128 KiB) |

A write of 0 to QueueNotify with the queue ready and DRIVER_OK set serves every request made available since the last one before the store completes: the device holds `ready` low, which the bus contract lets any device do, and meanwhile reads and writes RAM through the CPU's side of the RAM port, since the CPU is stalled on that very store. A request is a chain of exactly three descriptors: a header (type 0 IN or 1 OUT, and the sector) the device reads, a data buffer, device-writable for IN and not for OUT, and one status byte it writes. The data buffer must be word aligned and a whole number of words, and must fit the disk, or the status is 1 (IOERR); another type is 2 (UNSUPP). The device then writes the used-ring element (the head, and the bytes it wrote: the data and the status for an IN, the status alone otherwise), advances the used index and sets InterruptStatus bit 0. A chain it cannot follow (a NEXT or WRITE flag out of place, a nonzero high address word, a head or next index at or past QueueNum) or a DMA address outside RAM sets Status bit 6 (DEVICE_NEEDS_RESET) and serves nothing more until the status is written with 0. DMA is not checked against the graphics engines' write locks. QEMU serves requests after the notify returns and does not require word-aligned buffers; a driver waits for the used index on every platform.

The disk is 128 KiB. The emulator takes a file of exactly that size (`--disk FILE`) and writes each OUT request through to it, including the words an OUT had written when a DMA fault stopped it, so the file is always the disk the machine holds; if a write to the host file fails, that request and every later one reports IOERR. Without a file the disk is zeros for the run. The RTL keeps it in a memory inside the device (`DISK_WORDS`), which the testbench fills from `+disk=` (hex words) and saves to `+disk-out=` when the run ends; a reset does not clear it. The runner gives each backend its own copy of a disk image and requires both to end identical. Programs find the PLIC through the device tree (`riscv,plic0`) and a device's source through its `interrupts` property.

### Boot ROM at `0x0000_1000`

A 4 KiB read-only window holding the machine's device tree blob, generated by [rv32_dtb.py](../tools/rv32_dtb.py). Reads of every width return the blob's bytes (beyond the blob, zero); every write faults; the bus refuses fetches. Firmware reaches it through `a1` and never by this address, because on QEMU the tree is elsewhere ([Boot convention](#boot-convention)).

### Input at `0x1100_1000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Read word | `EVENT`: remove and return the oldest queued event, or 0 when the queue is empty |
| +4 | Read word | `COUNT`: events currently queued, 0 to 16 |
| +8 | Read word | `KEYS`: bit `k` set while key code `k` is held |

Every write and every byte or halfword access faults. An event word is `0` (none) or `0x8000_0000 | (press << 8) | code`: bit 31 marks a valid event, bit 8 is 1 for a press and 0 for a release, bits 4:0 hold the key code, and bits 30:9 and 7:5 are zero. Key codes are 0..31 so that `KEYS` can hold one bit per key; the named codes are in [board.h](../programs/rv32/board.h) (`LEFT` 1, `RIGHT` 2, `UP` 3, `DOWN` 4, `SPACE` 5, `ENTER` 6, `ESCAPE` 7, then letters), and the native window maps host keys to them ([Behavior fixed in M6](#behavior-fixed-in-m6)). `KEYS` changes when an event *arrives* in the queue, not when firmware pops it, so it reflects the host's keyboard state; a press and a release that arrive together leave the bit clear even before the events are read. The queue holds 16 events; the host drops an event that arrives when it is full and reports the drop on its diagnostic stream.

Where events come from: the host is a script on both backends, or the keyboard in the window (M6) (`frame N down KEY` and `frame N up KEY` lines, non-decreasing `N`, `KEY` a name from `board.h` or a number 0..31; a number is one to nine ASCII digits; a line whose first token begins with `#` is a comment, and trailing comments are not allowed). An event scheduled for frame `N` arrives in the queue when the present store that raises the frame count to `N` retires; frame 0 events are queued before the first instruction. Events with the same frame arrive in script order. Tying arrival to a guest-observable checkpoint rather than to a tick count is what makes the sequence identical on both backends. An event the script scheduled and the program never saw, because the queue was full or the frame was never presented, is reported after the halt line and turns a passing run into a failure (a nonzero exit status on both backends) unless the host was told to expect it (`--allow-lost-events`, `+allow-lost-events`): the guest's pass says nothing about events it never received. A guest that failed or was halted keeps its own outcome, since a firmware that stops early naturally leaves later events unread.

### Display at `0x1100_2000` and framebuffer at `0x1200_0000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Write word | `PRESENT`: present the framebuffer; faults while G1 is BUSY; the value is ignored |
| +4 | Read word | `FRAMES`: presents since reset |
| +8 | Read word | `WIDTH`: 320 |
| +12 | Read word | `HEIGHT`: 240 |

Reads of +0, writes to +4 to +12, and every byte or halfword access fault. The framebuffer window is 76,800 bytes of ordinary memory: one 8-bit pixel per byte, row-major from the top-left pixel, `WIDTH` bytes per row, readable and writable as bytes, halfwords, and words while G1 is not BUSY (CPU accesses fault during ownership); the byte after the last pixel faults. Its contents are unspecified at reset. A store to it is data movement and nothing else: nothing is visible until a present, when the backend takes a snapshot of the whole window. The snapshot becomes a checkpoint line `frame N <8 hex digits>` (the hash below) on every backend, and the native window shows it (M6). The pixel value is a color index with a fixed mapping, bits 7:5 red, 4:2 green, 1:0 blue (RGB332), each field scaled to full range (`r = field × 255 / 7`, `b = field × 255 / 3`); a palette was considered in M6 and deferred, and its window stays reserved.

The checkpoint hash covers pixel bytes only, in address order, as the 19,200 little-endian words of the window: `h = ((h << 5) + h) ^ word` starting from `h = 5381`, 32-bit arithmetic, printed as eight lowercase hex digits. It uses shifts and adds only because RV32I has no multiply instruction and the firmware computes the same hash over a frame it reads back; a palette added later never changes a recorded checkpoint.

### DMA window at `0x1100_a000`

| Offset | Access | Meaning |
| --- | --- | --- |
| +0 | Read/write word | `START`: the first byte of RAM the engines may reach; `0x8000_0000` at reset |
| +4 | Read/write word | `END`: one past the last; `0x8000_0000` plus the RAM size (`0x8040_0000`) at reset |

Byte and halfword accesses fault, and so does every other offset in the page. G1's blit source and G2's depth buffer must lie in [`START`, `END`) as well as in RAM: G1's SETUP ends a blit whose RAM source leaves the window with `ERROR` = `INVALID`, and G2's VALIDATE ends a job or `CLEAR_Z` whose depth buffer leaves it with `E_PARAM`. G1's framebuffer source is not RAM and ignores the window. The engines test the window only when they validate a job, so a write never affects a job already running, and writes are accepted at any time. At reset the window is all of RAM, so a program that never writes it sees the engines exactly as before.

The window is how a kernel keeps a program it lets drive the engines inside that program's own memory ([rv32-os.md](rv32-os.md#o5-protection)): PMP holds the CPU, not DMA. It sits alone in its page, above the engines' windows, so a PMP region or page mapping that grants the engines leaves it out. Test: `make test-rv32-dma-window` (`tests/test_rv32_dma_window.py`, emulator and RTL).

### Device time

The emulator executes one instruction per loop iteration and knows nothing about clocks; the RTL takes 4 or 5 cycles per instruction plus stalls. A tick is therefore backend-specific:

| Backend | One tick | Origin | What a read returns |
| --- | --- | --- | --- |
| RTL | One clock cycle | The first rising edge after reset release is cycle 1 | The count in the cycle the bus accepts the read: a `lw` accepted in cycle `k` reads `k` |
| Emulator (every mode) | One executed instruction (retired or trapped) | The first instruction is step 1 | The count before the reading instruction: a load inside instruction `N` reads `N − 1` |

A written value replaces the count and the rate continues. Since O1 the RTL also has a deterministic **step-tick mode** (`+ticks=steps`): the CLINT's `mtime` and the core's `cycle` then advance once per step, an instruction retired or trapped or an interrupt taken, and `wfi` does not wait, so every read of device time and every timer interrupt happens at the same instruction as on the emulator, and interrupt-driven programs keep trace comparison. Accelerators still advance per clock in that mode. M6 decided against a host-time mode: the window paces presents instead, and the timer (since Track 1 the CLINT's `mtime`) counts instructions in every mode, so a session recorded in the window replays exactly on every backend. Input arrival is keyed to frames; presents and checkpoints happen at the accepting store, console bytes and the done word at their stores. A2 adds an autonomous accelerator: it advances once per RTL clock or emulated CPU instruction (including traps), with STATUS and counters observed before the accepting emulator instruction's tick. Emulator accelerator STALLS is always zero; RTL test inputs may delay transfers. Timer waits and accelerator polling therefore use result-level comparison rather than identical CPU traces.

## Firmware image and ABI

The image is an ELF32 little-endian executable: `e_machine` 243 (RISC-V), `e_type` `ET_EXEC`, `e_flags` 0 (no compressed instructions, soft-float ABI), `Tag_RISCV_arch` `rv32i2p1`. One `PT_LOAD` segment starts at `0x8000_0000` with load address equal to run address, so startup copies nothing. Section order and symbols come from [link.ld](../programs/rv32/link.ld):

| Section or symbol | Meaning |
| --- | --- |
| `.text` | Code; `.text.init` from [start.S](../programs/rv32/start.S) is kept first so `_start` is at `0x8000_0000` |
| `.rodata` | Constants and string literals |
| `.data`, `__data_start`, `__data_end` | Initialized globals, already in place when loaded |
| `.bss`, `__bss_start`, `__bss_end` | Zero-initialized globals, word aligned, zeroed by `_start` |
| `_end` | First free byte after `.bss` |
| `_stack_bottom`, `_stack_top` | 16 KiB stack at the top of the 256 KiB slice; `_stack_top` is 16-byte aligned |

Startup sets `sp`, zeroes `.bss` one word at a time, calls `main`, then falls into `rv32_exit`, which converts `main`'s return value (0 pass, 1..255 fail) into the done word. No global pointer is set up because linker relaxation is disabled; no thread pointer or heap exists.

Compiler and linker flags, from the [Makefile](../Makefile):

| Flag | Reason |
| --- | --- |
| `--target=riscv32-unknown-elf -march=rv32i -mabi=ilp32` | Base ISA only; soft-float ILP32 objects |
| `-mcmodel=medlow` | Absolute `lui`/`addi` addressing; on RV32 it spans the whole address space, so `0x8000_0000` is fine and linked addresses are visible in listings |
| `-mno-relax` | The linker leaves instruction sequences as compiled, so object and linked listings match line for line; enabling relaxation is an exercise |
| `-ffreestanding -fno-builtin -nostdlib -static` | No hosted C library, no implicit calls except the arithmetic libcalls we supply |
| `-O2 -g` | Real code generation with source interleaved in the listing |
| `-fno-asynchronous-unwind-tables -fno-unwind-tables` | No `.eh_frame`; the image checker rejects unexpected allocated sections |
| `--ld-path=/opt/homebrew/opt/lld/bin/ld.lld` | Explicit linker; `-fuse-ld=lld` would search the compiler's own directory and then `PATH` |

### Runtime routines

Clang lowers 32-bit `*`, `/`, and `%` on an RV32I target to calls named `__mulsi3`, `__divsi3`, `__udivsi3`, `__modsi3`, and `__umodsi3`. Homebrew's LLVM ships no compiler-rt for RISC-V, so [muldiv.c](../programs/rv32/rt/muldiv.c) provides them as aliases of `rv32_mul`, `rv32_div`, `rv32_divu`, `rv32_rem`, and `rv32_remu`. Results follow the RISC-V M extension exactly: division by zero yields all ones (`-1`) with the dividend as remainder; `INT32_MIN / -1` yields `INT32_MIN` with remainder 0; signed quotients truncate toward zero. Future `MUL`/`DIV`/`REM` hardware must agree with these routines. The same file compiles natively so [test_rv32_rt.py](../tests/test_rv32_rt.py) can compare it with Python integers at `-O0` and `-O2`.

The signed routines work on unsigned magnitudes and fix up the sign afterwards, so `INT32_MIN` is never negated as a signed value.

### Image outputs and checks

`make firmware-rv32` writes `build/rv32/selfcheck.elf`, `.lst` (disassembly with source), `.bin` (flat image from `0x8000_0000`), `.map`, and `.readelf`, and since M5 the same five files for `diag`, the device diagnostic ([record](rv32-soc.md#the-diagnostic)), which links [trap.S](../programs/rv32/trap.S) as well. `make check-rv32-image` runs [rv32_image.py](../tools/rv32_image.py), a standard-library ELF32 parser whose flattened `.bin` is what the emulator loads. It rejects an image unless: class, byte order, machine, type, and `e_flags` match the contract; the entry point, `_start`, and the lowest load address are all `0x8000_0000`; every load segment is word aligned, has equal load/run addresses, and lies inside the 256 KiB slice; `.text`, `.rodata`, `.data`, `.bss` exist and no other allocated section does; the `.bss` symbols match the section; the stack follows `_end` inside RAM with a 16-byte aligned top; no symbol is undefined; the listing contains no undecodable instruction and no `mul*`, `div*`, `rem*`, `csr*`, `c.*`, `fence.i`, `ecall`, `ebreak`, `wfi`, or `*ret`. The diagnostic is checked with `--allow-privileged`, which admits `csr*` and `mret` for its trap handler and nothing else. It also writes `build/rv32/selfcheck.hex`, little-endian 32-bit words from `0x8000_0000` for `$readmemh`, and verifies the `.bin` written by `llvm-objcopy` equals its own flattening byte for byte.

## Behavior fixed in Track 0

The machine is now RV32IMF with Zicsr and Zicntr ([Track 0 record](rv32-groundwork.md)):

- The M extension's eight instructions (`mul`, `mulh`, `mulhsu`, `mulhu`, `div`, `divu`, `rem`, `remu`) as the unprivileged specification defines them. None traps: division by zero gives an all-ones quotient and the dividend as remainder, and `INT32_MIN / -1` gives `INT32_MIN` and remainder 0. Every other `funct7` on the OP opcode is still illegal. RV32I firmware stays valid; RV32IM builds need no software multiply or divide.
- The Zicntr counters `cycle` (0xc00), `time` (0xc01), `instret` (0xc02) and their high halves (0xc80–0xc82) are read-only CSRs: `csrrw`/`csrrwi` on them, or `csrrs`/`csrrc` (immediate forms too) with a nonzero rs1 field, is an illegal instruction, as is any other counter number (`mcycle`, `hpmcounter3`...). A read of `instret` returns the instructions retired before the reading one, on every backend. A read of `cycle`, or of `time` until Track 1 re-sourced it from `mtime` (below), returns, on the emulator, the instructions executed before the reading one and, on the RTL, the clock cycles up to the reading instruction's `EXECUTE` state, its own `FETCH` and `DECODE` included (`4k + 2` for instruction *k* after reset, counting from 0, with no stalls or waits).
- `instret` counts retired instructions since reset, identical on every backend. `cycle` and `time` count device ticks ([Device time](#device-time)): clock cycles on the RTL, executed instructions (retired or trapped) on the emulator, and until Track 1 `time` equalled `cycle` on both. Since Track 1 `time` reads the CLINT's `mtime`: before any write to `mtime` it equals `cycle` on the emulator and `cycle + 1` on the RTL (`mtime` counts the reading cycle itself), and after a write it differs on both. A program that reads `cycle` or `time` is compared at the results level, like one that reads the timer; one that reads only `instret` keeps trace comparison. Track 1 re-sourced `time` from the CLINT's `mtime` (below).

## Behavior fixed in Track 1

The platform is compatible with QEMU's `virt` board wherever `virt` has a device ([Track 1 record](rv32-platform.md)):

- The memory map above: our windows moved out of `virt`'s ranges, the CLINT replaced the timer, the boot ROM holds the device tree, and `virt`'s PLIC and virtio-mmio addresses are reserved (unmapped) for O1 and O3.
- `time` and `timeh` read the CLINT's `mtime`, so a write to `mtime` moves them, as on QEMU; `cycle` stays the core's own count. Before any write the two agree on the emulator (both count executed instructions); on the RTL `time` reads the count of the reading cycle, one more than `cycle` there.
- The boot convention below. RTL register reset values follow it: `x11` resets to `0x0000_1000`, every other register to 0.

### Boot convention

At the first instruction `a0` holds the hart id and `a1` the address of a flattened device tree (Devicetree Specification v0.4, format version 17), exactly as QEMU's `virt` mask ROM leaves them. On QEMU the tree is QEMU's own, in RAM near the top of the 4 MiB; on our emulator and RTL it is the boot ROM's. [start.S](../programs/rv32/start.S) calls `main` without touching `a0` or `a1`, so a program declared `int main(uint32_t hart, uintptr_t tree)` receives both; [fdt.c](../programs/rv32/fdt.c) reads the tree.

Our tree names our own devices with `tiny-processors,*` compatible strings and adds a generic one only where the device implements everything a driver for it may touch: the done register is also `sifive,test0` (without the reset word), the CLINT also `riscv,clint0`; the console, only a 16550's transmit and line-status registers, is not claimed as `ns16550a`. It has no `timebase-frequency`: the contract gives device ticks no rate. The rule for a program that runs on more than one platform is to use a device only when the tree lists it.

## Behavior fixed in Track 2

Track 2 builds an operating system one step at a time ([plan](planning/track2-os.md), [record](rv32-os.md)).

### O1: interrupts

- **CSRs.** `mstatus` (0x300): MIE (bit 3) and MPIE (bit 7) are writable; MPP (12:11) read 3 until O5 made it writable ([O5](#o5-protection)), FS (14:13) reads 3 and SD (31) reads 1, because floating state is always on; every other bit reads 0. `mie` (0x304): MSIE, MTIE and MEIE (bits 3, 7, 11) are writable, the rest read 0. `mip` (0x344): MSIP, MTIP and MEIP are the live levels from the CLINT and the PLIC; a write is legal and changes nothing. `mscratch` (0x340): 32 bits. RISC-V's architectural tests' `csrs mstatus, a0` therefore retires instead of trapping. Issue #20 made the supervisor's bits of all three writable too ([S-mode and Sv32](#s-mode-and-sv32-issue-20)).
- **Taking an interrupt.** Before an instruction is fetched, if `mstatus.MIE` is set and `mip & mie` is nonzero, the highest-priority pending interrupt is taken instead: MEI (11), then MSI (3), then MTI (7). `mcause` is `0x8000_0000 | code`, `mepc` the PC of the instruction not executed, `mtval` 0, and as for an exception MPIE takes MIE and MIE clears. `mret` sets MIE from MPIE and MPIE to 1. An interrupt entry is a step (a device tick on the emulator) and a trap for the double-fault rule; on the RTL it costs one cycle and is taken only in place of a fetch not yet presented, so a request on the bus is never withdrawn. Issue #20 adds the supervisor interrupts, their enables and where they rank ([S-mode and Sv32](#s-mode-and-sv32-issue-20)).
- **Trace.** An interrupt entry is the line `<step> <pc> 00000000 interrupt <code>` on both backends; the halt lines count them (`interrupts=N`, when nonzero). Results comparison leaves interrupt entries out of the trap records, since device time decides where they land.
- **`wfi`** (`0x1050_0073`) retires. On the RTL with cycle ticks it first waits until `mip & mie` is nonzero, whatever MIE says; on the emulator and in step-tick mode it retires at once. Both are allowed by the specification, so programs wait with `wfi` in a loop.
- **The PLIC** above, and the device tree's interrupt wiring: the hart's `riscv,cpu-intc` (phandle 1), the CLINT's `interrupts-extended` (MSI and MTI), the PLIC wired to MEI with `riscv,ndev = 31`, and the input node's `interrupts = <12>`.
- **Step-tick mode** on the RTL ([Device time](#device-time)).

### O2: a kernel and system calls

- The console's receive side (above).
- The program layout and system calls are software, not machine contract; [the Track 2 record](rv32-os.md#o2-a-kernel-and-system-calls) and [sys.h](../programs/rv32/os/sys.h) define them. The kernel image is 1 MiB at `0x8000_0000`; programs are linked for slots above it (256 KiB in O2, 128 KiB since O4).

### O3: storage

- virtio-blk at `0x1000_1000`, PLIC source 1 (above), in the device tree as `virtio_mmio@10001000` (`virtio,mmio`, `interrupts = <1>`); the map checker requires it to lie inside `virt`'s first virtio slot.
- The file system is software ([rv32-os.md](rv32-os.md#o3-storage), [rv32_mkfs.py](../tools/rv32_mkfs.py)).

### O4: preemptive multitasking

No change to the machine: the scheduler is software ([rv32-os.md](rv32-os.md#o4-preemptive-multitasking)). The runner learned to compare exception records per 128 KiB region of their PC, and optionally without environment calls, and to compare only the number of checkpoints for frames that depend on scheduling.

### O5: protection

- **User mode.** The hart has two privilege modes, machine (3) and user (0), and starts in machine mode (issue #20 adds supervisor mode between them; [S-mode and Sv32](#s-mode-and-sv32-issue-20)). `mstatus.MPP` is WARL: a write of 3 keeps 3 and any other value stores 0 (since issue #20 a write of 1 keeps supervisor mode; only the reserved 2 stores 0). A trap, exception or interrupt, puts the mode it came from in MPP and enters machine mode (unless delegated to S mode since issue #20); `mret` enters the mode MPP names and sets MPP to 0. `ecall` from user mode is cause 8 (`mtval` 0). In user mode an access to a CSR whose privilege field (bits 9:8) is nonzero, which includes every machine CSR, and `mret` and `wfi` are illegal instructions (and `sret` and `sfence.vma` since issue #20); the floating CSRs are allowed, and a counter only when its bit is set in `mcounteren` (0x306: CY bit 0, TM bit 1, IR bit 2, the rest read 0; 0 at reset), and since issue #20 in `scounteren` too. In user mode interrupts are enabled whatever `mstatus.MIE` says, since a lower mode can never mask machine interrupts; `mie` still selects them.
- **PMP.** Eight entries: `pmpcfg0` and `pmpcfg1` (0x3a0, 0x3a1) hold a byte each, `pmpaddr0` to `pmpaddr7` (0x3b0 to 0x3b7) a word address (bits 33:2 of the byte address, of which the machine's 32-bit space uses 31:2). A byte is R (bit 0), W (1), X (2), A (4:3: OFF, TOR, NA4, NAPOT) and L (7); bits 6:5 read 0, and W without R, which is reserved, is stored as neither. Every entry resets to 0 (OFF). TOR matches `pmpaddr[i-1] <= a < pmpaddr[i]` on word addresses (0 below entry 0), NA4 one word, NAPOT the power-of-two region of 2^(k+3) bytes that `k` trailing ones encode; the granularity is 4 bytes. The lowest-numbered entry that matches decides. User mode (and supervisor mode since issue #20) needs a matching entry with the permission (X to fetch, R to load, W to store); an access nothing matches fails. Machine mode is held only by a matching locked entry and passes where nothing matches. A locked entry ignores writes to its byte and its `pmpaddr` until reset, as does the `pmpaddr` below a locked TOR entry. A refused access never reaches the bus: fetch, load or store access fault (1, 5, 7) with the address in `mtval`, the fetch's before the instruction is read, a load's or store's after the misalignment check.
- **Trace.** Unchanged: the trace shows no mode. The emulator's `--dump-state` adds a `priv` line.
- **The kernel** runs every program in user mode with PMP granting its slots, the framebuffer and, for a program that drives them, the accelerators ([rv32-os.md](rv32-os.md#o5-protection)).
- **PMP holds the CPU only.** G1's and G2's DMA reads and writes RAM wherever their registers point, as virtio-blk's does, so a program granted the engines' windows could reach any RAM through them. Issue #20 closed that with the [DMA window](#dma-window-at-0x1100_a000): the kernel sets it to the running program's slots, and the engines refuse a blit source or depth buffer outside it.

## S-mode and Sv32 (issue #20)

The hart gains supervisor mode and Sv32 paging, on the emulator and the RTL alike. [mmucheck](../programs/rv32/mmucheck.c) (57 checks, `PASS 7530cb0f`) runs on QEMU `virt` with `-cpu rv32,svade=on,svadu=off`, the emulator, Icarus and Verilator, and is trace-identical in step-tick mode. [tests/test_rv32_mmu.py](../tests/test_rv32_mmu.py) covers what QEMU cannot referee or mmucheck leaves out. The kernel still runs its programs on PMP alone; paging them is [#25](https://github.com/ahmad-luqman/tiny-processors/issues/25).

- **Modes.** Machine (3), supervisor (1) and user (0). `mstatus.MPP` is WARL {3, 1, 0}; `SPP` is one bit.
- **mstatus** adds SIE (1), SPIE (5), SPP (8), MPRV (17), SUM (18), MXR (19), TVM (20), TW (21) and TSR (22). `sstatus` (0x100) is its view of SD, MXR, SUM, FS, SPP, SPIE and SIE.
- **Delegation.** `medeleg` (0x302) holds exceptions 0 to 9, 12, 13 and 15; `mideleg` (0x303) the supervisor interrupts SSI (1), STI (5) and SEI (9). A trap from S or U mode whose bit is set enters S mode: `sepc`, `scause`, `stval`, SPIE takes SIE, SIE clears, SPP takes the mode, `pc` = `stvec` (direct mode). A trap from machine mode always stays there.
- **Interrupts.** `mie` and `mip` add SSIE/SSIP, STIE/STIP and SEIE/SEIP. Nothing drives the supervisor interrupts but software: machine mode writes them in `mip`, and S mode may write SSIP in `sip` when it is delegated (there is no PLIC context for S). `sie` and `sip` show the delegated bits. Interrupts bound for machine mode (not delegated) are taken before those bound for S mode, and within one mode the order is MEI, MSI, MTI, SEI, SSI, STI, so a pending SSI that machine mode keeps goes before a delegated SEI. An interrupt handled in machine mode is enabled below it whatever MIE says; a delegated one below S mode, or in it with SIE, and never in machine mode. No interrupt is taken before a trap handler's first instruction retires, so an interrupt cannot make a double fault of a trap into S mode; an exception there still does, at either level.
- **Instructions.** `ecall` from S mode is cause 9. `sret` restores SIE from SPIE, sets SPIE, enters the mode SPP names and clears SPP; `sret` always clears MPRV, and `mret` does when it leaves machine mode. `sfence.vma` is legal in S and M mode (any rs1 and rs2; there is no TLB to flush). In S mode, TSR makes `sret` illegal, TW `wfi`, and TVM `sfence.vma` and any access to `satp`. User mode may use none of them.
- **CSRs.** `stvec`, `sscratch`, `sepc`, `scause`, `stval`, `scounteren` and `satp` (0x180). A CSR needs the privilege its number's bits 9:8 name. A user-mode counter read needs its bit in both `mcounteren` and `scounteren`; S mode needs only `mcounteren`.
- **Sv32.** With `satp.MODE` set (bit 31; PPN in bits 21:0; the ASID is 0 bits wide), fetches below machine mode and loads and stores below it at their effective privilege are translated. The effective privilege is MPP's in machine mode with MPRV set, and the mode's own otherwise; it also decides PMP for data. The walk is two levels with 4 MiB megapages. A page fault (12 fetch, 13 load, 15 store) or an access fault from the walk puts the virtual address in `mtval`/`stval`. In order:
  - Misalignment is checked on the virtual address first. The privileged spec allows either order; QEMU translates first and page-faults, so mmucheck leaves that case out and test_rv32_mmu.py pins ours.
  - Each entry read is a supervisor read: PMP must grant it, it must be in the 32-bit space, and only RAM answers it (a device window or an unmapped address is an access fault of the access's own kind).
  - V clear, or W without R, is a page fault. A pointer with D, A or U set, or at level 0, is a page fault. A megapage whose PPN is not 4 MiB aligned is a page fault.
  - U-mode needs U; S mode faults on a U page for a fetch, and for data unless SUM. A fetch needs X, a store W, a load R or, with MXR, X.
  - A and D are never set by hardware (Svade): a clear A, or a clear D on a store, is a page fault.
  - A physical address at or past 2^32 is an access fault. PMP then checks the physical address.
- **No TLB.** Every translated access walks, which is what a TLB must look like to a program that follows each page-table change with `sfence.vma`. A TLB is [#24](https://github.com/ahmad-luqman/tiny-processors/issues/24).
- **Tools.** The emulator's `--dump-state` adds `medeleg`, `mideleg`, `satp`, `stvec`, `sepc`, `scause` and `stval`, and a double fault whose first trap went to S mode reports `scause`, `sepc` and `stval`. The GDB stub reads and writes memory by physical address, whatever `satp` says.
- **RTL.** Two states: `WALK` reads one entry per visit (1 cycle plus stalls), and `XLATE` checks PMP on a translated data address (1 cycle). A translated fetch costs its deciding `FETCH` cycle and one `WALK` per level; a translated load or store one `WALK` per level and `XLATE`. The core's `mem_ptw` marks a page-table read; the SoC hands the bus `mem_fetch || mem_ptw`, so only RAM answers it. With `satp.MODE` clear the timing is unchanged to the cycle.
- **Cost.** The core grows from 48,818 to 53,212 generic cells (Yosys 0.69, `synth -top rv32`, both measured on this toolchain), still latch-free: 4,394 cells for the supervisor CSRs, delegation, the walker and the PMP privilege mux.
- **Trace.** A data access shows its virtual address on both backends. The testbench's halt line adds `walks` (page-table reads) and `ptw_waits` (the walk's cycles, stalls apart) when a run walks, and the cycle formula adds `ptw_waits`; transfers are then the fetches, the data accesses and `walks`.
