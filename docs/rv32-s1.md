# S1: the integrated SoC

S1 runs 2D graphics, programmable 3D and digit inference from one boot of one
firmware image, and proves the three accelerators behave correctly next to each
other. No RTL changed: S1 specifies the overlap rules the machine already had,
tests them end to end, and records what the whole machine costs.

Two artifacts carry the evidence:

| Artifact | What it proves | Commands |
| --- | --- | --- |
| `programs/rv32/soc.input`, a 185-frame menu session | The boot menu drives G1, G2 and SIMD4 in one session and every frame matches the C references | `make run-rv32-soc-menu-emu`, `run-rv32-soc-menu-rtl-verilator`, `run-rv32-soc-menu-rtl` |
| `programs/rv32/soccheck.c`, an eleven-case diagnostic | Each pair of engines overlaps or is refused as the contract says, and a reset or fault in one leaves the others exact | `make run-rv32-soc-emu`, `run-rv32-soc-rtl-verilator`, `run-rv32-soc-rtl` |

The overlap contract lives in the SoC record, [Accelerator overlap](rv32-soc.md#accelerator-overlap):
G1 and G2 exclude each other because they share one engine memory port; SIMD4
has private memories and runs alongside either.

## The menu session

One boot, in this order:

1. UP wraps to the 2D demo. G1 draws each frame; SPACE switches to the CPU path
   and back.
2. The 3D demo. G2 draws the cube; SPACE changes the shader and R restarts.
3. The digit screen. A 20-cell vertical stroke is drawn and ENTER classifies it
   on SIMD4 and on the CPU (the firmware stops if they disagree). It reads as a 1.
4. The 2D demo again, after both other engines have been used, then Q.

The checkpoints are pinned from the native build, where the C references draw
(`tools/rv32_capstone_native.py --input programs/rv32/soc.input --write`). On
the emulator and the RTL the devices draw, so matching all 185 checkpoints holds
the hardware to the references frame by frame. `PASS c76cd363` is the runtime
checksum over the whole session (it was `bc4f7607` until the digit size fix
retrained the model).

A pinned session proves only that a run is repeatable, so
`test_soc_session_visits_every_engine` also asserts the screens the session
drew (menu, 2D, menu, 3D, menu, digit, menu, 2D, menu), that every 3D frame
rendered with status 0, and that exactly one classification ran and read 1.

The Verilator run seeds random waits on all three memory paths at once: CPU
memory (`--seed 17`), the shared engine port (`--gpu-seed 31`) and the SIMD4
buffers (`--simd-seed 43`). No earlier run stressed the three together.

## The diagnostic

A keyboard replay cannot inject a fault, so `soccheck` does that part. It
installs the M5 trap handler, which records each trap and skips the faulting
instruction, and checks each case's traps exactly.

| Case | What runs | Checked |
| --- | --- | --- |
| `sequential` | G1 full-screen fill, G2 scene 0, one digit inference, one after another | Frame hash, every G2 counter, both images, all ten logits |
| `g1-refused-while-g2` | G1 START during a G2 scene | One store fault at G1 COMMAND, G1 status unchanged, G2 exact |
| `g2-refused-while-g1` | G2 START and CLEAR_Z during a G1 fill | Two store faults at G2 COMMAND, G2 status unchanged, G1 exact |
| `g2-owns-display` | Framebuffer store and load, PRESENT, depth-buffer store during a G2 scene | Faults 7, 5, 7, 7 at those addresses, G2 exact |
| `simd4-alongside-g2` | A whole inference during a G2 scene | Both exact, no traps |
| `simd4-alongside-g1` | A whole inference during a G1 fill | Both exact, no traps |
| `g2-inside-simd4` | CPU draws and presents during a SIMD4 launch; then a whole G2 scene inside one launch | No traps; SIMD4 still BUSY when G2 finishes |
| `reset-isolation` | G1 and SIMD4 RESET during a G2 scene; G2 RESET during a G1 fill and a SIMD4 launch | The running engines finish exact or stay BUSY |
| `fault-isolation` | SIMD4 illegal opcode during a G2 scene; G2 parameter fault during a SIMD4 launch | The faulting engine reports FAULT, the other is unaffected |
| `reset-hands-over-port` | RESET a busy G2, then G1 START; RESET a busy G1, then G2 START | No traps, the cancelled engine reads IDLE, the new job is exact |
| `recovered` | One more inference and scene | Both exact |

Two rules keep the cases independent of timing. Each forbidden access is made
only after reading the owning engine's STATUS as BUSY, so no backend can finish
first and turn a fault into a legal access. And every overlap is arranged so the
job that must still be running is the longer one on every backend. The first
emulator runs showed why both rules matter. The CPU's 2D reference render costs
more instructions than a whole G2 scene, so drawing it after START let the scene
finish before the refused START. Hashing a frame costs more than the scene too,
so SIMD4's BUSY is checked before the hashes, not after.

The G2 counters are compared as CYCLES − STALLS. The CPU competes with G2 at the
RAM arbiter, so G2's STALLS depend on what the CPU does meanwhile, and only the
work cycles are fixed by the oracle.

Exit codes are 100–152, one per check in order,, distinct from the milestone diagnostics (1–44) and the
capstone (80–86).

## Measurements

Device time differs between the backends by design, so every figure below is
measured and none is compared across backends except the results. Wall times
are on the development Mac and are not part of any contract.

| Run | Emulator instructions | RTL instructions | RTL cycles | RTL stalls | Wall time (Verilator) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `soccheck`, Verilator, `--stall 1 --gpu-stall 2 --simd-stall 2` | 8,004,863 | 6,653,047 | 36,285,085 | 8,314,358 | 30 s |
| `soccheck`, Icarus, no injected waits (S1, before the digit size fix) | 7,970,297 | 6,447,353 | 27,100,757 | 2,399 | about 28 min on Icarus |
| Menu session, Verilator, seeded waits on all three paths | 19,081,727 | 15,113,499 | 90,332,697 | 26,954,140 | 77 s |

The Verilator rows were re-measured after the digit size fix, whose resize adds
CPU work to every digit inference; the Icarus row is S1's and was not rerun.

The emulator retires more instructions than the RTL for the same run. Its
devices tick once per instruction while the RTL's tick once per cycle, and the
RTL averages 5.5 to 6 cycles per instruction in these runs (stalls included), so
a polling loop spins several times more often on the emulator.

Per-engine costs were measured by each milestone and no RTL or driver changed in
S1: G1 in the [G1 record](rv32-gfx.md), one digit inference in the
[N1 record](rv32-digit.md), and one 3D frame (363,777 device cycles) in the
[G2 record](rv32-3d.md). The digit size fix, after S1, added a resize to the
digit preprocessing; a digit inference still makes 13,592 SIMD4 transfers, but
its CPU cost grew, and the N1 record has the current figures.

### Synthesis

`make synth-rv32-soc` (yosys, both memories shrunk to 64 words so the count
measures logic, not storage; no latches) rerun on the S1 branch gives
**327,986 cells and 45,666 flip-flops**, identical to G2's figure because no RTL
changed. It took 149 s. Per block, adding each module's own cells to its
submodules' (yosys lists them separately):

| Block | Cells |
| --- | ---: |
| G2: `rv32_g3d` 119,296 + shader core 43,437 (162,679 when synthesized alone; ABC's result moves with the module set around it) | 162,733 |
| SIMD4: wrapper and windows 40,854 + four-lane engine 13,018 | 53,872 |
| G1: `rv32_gpu` | 52,022 |
| CPU: `rv32` 3,469 + `fp32` 25,515 + register files 11,667 + ALU and decoders 1,520 | 42,171 |
| RAM and framebuffer, 64 words each | 13,434 |
| Bus, input, console, timer, display, done, SoC glue | 3,754 |
| Whole SoC | 327,986 |

The two engines that share the port cost 214,755 cells together, two thirds of
the machine. Letting them overlap would add a second engine port or arbiter on
top of that, and nothing measured yet needs it, so S1 keeps the exclusion.

### Acceptance run

The full `make test-rv32` aggregate, which now includes the S1 diagnostic and
session on the emulator and Verilator, passed on the S1 branch with exit status 0:
315 unit tests and every replay, lint and synthesis step, in 26 min 36 s.

## Behaviour worth knowing

- The firmware treats device failures unevenly. A G1 or G2 failure, or a
  disagreement between the SIMD4 and CPU digit paths, ends the run with an exit
  code (80–86), so the 3D demo's "DEVICE ERROR" screen cannot appear on real
  hardware. A SIMD4 status other than OK is drawn on the digit screen instead.
  Making G1 and G2 report on screen too would be a small follow-up.
- SIMD4 is still initialized on first use. `capstone.input` never enters the
  digit screen, so its replay stays trace-identical.

## Digit accuracy on drawn input (fixed after S1)

Hand testing during S1 found that the digit screen misread digits drawn much
smaller or larger than 20 cells: preprocessing centred the drawing but never
resized it to MNIST's 20-pixel box. The session's stroke is 20 cells tall for
that reason. [The digit size fix](planning/digit-size-fix.md#outcome) landed
after S1: it adds the resize, retrains the model and re-pins this session; the
stroke still reads 1.

## Exercises

1. **Let G1 and G2 overlap on paper.** Sketch what `rv32_soc.v` would need: a
   second engine port or a per-transfer arbiter, and who owns the framebuffer
   when both draw. Which `soccheck` cases would change their expected traps?
2. **Break the ownership rule.** Make the emulator allow a framebuffer store
   while G2 is busy and run `make run-rv32-soc-emu`. Which case fails, and with
   which exit code?
3. **Measure the arbiter.** Print G2's STALLS in `simd4-alongside-g2` and in
   `sequential` on Verilator, and explain the difference from the CPU's
   instruction mix during each.
